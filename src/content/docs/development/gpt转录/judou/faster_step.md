# 更快的步进限制系统（Faster Step）

## 动机

给下一代 WenyanRunner 做一个**更快的步进（step）限制系统**。

### 现在这套有什么问题

目前的步进限制系统存在两个主要问题：

1. **函数太贵**：在需要「指令级优化」的场景下，函数调用仍然很费。
2. **阻塞方式冲突**：现在用的是 **Java 的锁** 来做阻塞，这跟当前「用线程池里的上下文切换做阻塞」的实现**很冲突**。

### 基本需求（必须先满足）

1. **步进不超限**：实际执行步数不得超过上限，同时应尽量使用本轮可用额度。
2. **线程安全**：必须线程安全，不能导致程序出现意外行为。

## 设计

### 核心行为

用「**切片（slice）**」的思路运行：

- 每次运行器的执行量是 `min(slice, steps)`（取切片大小和剩余步数的小者）。
- 每步跑完后，用「已跑步数」去减总步数。
- 当 `steps == 0` 时，就不再运行。

### 加步（add step）的时机

每加 1 步：

1. **没有进程在等待 / 运行**（即没有步数剩余、也没有运行中的线程）时：直接加。
2. **有进程在运行**时：步数会在**当前进程结束后**、或**在下一个进程开始时**（跟下一次启动同步）再加。如果没有下一个进程，就退化回情况 1。

### 线程安全性论证

挨个情况证明：

1. **没有进程在运行**：只有「加步」这一个操作在读写步数，安全。
2. **正在运行**：也就是步数是在某个 slice 内部被加的。那么两次「加步」调用之间，最多跑过的步数 = 上一次 slice 的最大值 + 当前步数 = **最多两个 slice 的量**。

### 更进一步的实现技巧

可以用一个 **bool 标记**「是否已经调用过 add step」，并把「加步」作为**新队列的 offer**。证明思路：

- 如果**没有进程在运行**，没人访问步数，第一个访问者就是下一个运行的进程——所以「在运行前改」和「在调用发生时改」效果相同。
- 如果**有进程在运行**，跟上面分析的行为一致。

### 运行进程的条件

运行进程的条件就变成：

- **有步数剩余** → 跑。
- **没步数剩余** → 阻塞。
- 而 `addStep` 的调用会**唤醒**它。

其他地方的「获取步数」可以认为不变，只是在运行时不会被改写。

### 没有忙等（no busy wait）

当步数用完时，队列**不应该再提交线程**，避免空转。实现方式是：**用一个「会阻塞直到新步数到达」的阻塞队列**，可以做成**现有阻塞队列的包装器**。

### 与现有 slice 系统结合

设计上把「步数」和现有的「切片」系统结合起来：**步数用完 = 切片结束**。

### 同步问题

运行器可能因为「切片结束 / 阻塞」而**提前停止**。这时需要同步「已用步数」的信息：

- 在线程**开始时**读取步数。
- 在**切片结束时**写回。
- 这个读写应该由 **programImpl 包装**，因为步数理应由程序（program）来维护。

## 总结

更快的步进限制 = 用「切片 + 步数」结合的方式，替换掉昂贵的函数调用和冲突的 Java 锁阻塞。核心是：执行量取 `min(slice, steps)`、加步时机分「空闲直接加 / 运行中同步加」、用「无步数不提交线程」的阻塞队列避免忙等，并把步数的读写统一由 program 维护以保证线程安全。

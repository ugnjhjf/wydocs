# 元函数信息 / WenyanDoc

## 概述

函数元数据用于描述函数用途、参数要求、返回值和代码片段模板，使玩家可以在游戏内完成查询和输入，无需依赖外部 Wiki。

它有两个非常接地气的痛点要解决。

## 用户痛点（User Story）

**痛点一：查用法太费劲。**
玩家从一个包里 import 了一个函数，但不知道怎么用。按现在的流程，他得切出游戏、打开文言 wiki 慢慢找。这个过程又慢又打断游戏节奏——明明是游戏内的事，却要依赖游戏外的信息。

**痛点二：补全太鸡肋。**
玩家想用某个函数，先敲 `shi`，然后还得腾出手去鼠标点一下那个函数——而点这一下**只帮他填了函数名**。如果能像「代码片段（snippet）」一样，点一下直接把整条函数语句补全，体验会好得多。

## 设计要求

做这个系统，有几条硬性要求：

1. **可查**：玩家能获取任意函数的「描述、参数需求、返回值」。
2. **可补全**：程序能根据函数信息，自动生成正确的代码片段。
3. **适配动态代码**：系统要能适配**只能在 wy 程序运行后**才能生成的那些动态内置代码。
4. **客户端使用**：展示和补全所需的元数据应由客户端访问，避免无必要地增加服务端状态。
5. **改动最小化**：新系统对现有代码的侵入要尽量小，遵循 SOLID 原则。
6. **性能敏感**：作为一个基础系统，会被非常广泛地使用，内存和效率都得认真考虑。

## 一个关键难题：内存爆炸

同一个「元数据」可能对应很多个不同的「函数实例」。举个例子：一个「方块实体包」的 `package`，放在 999999 个不同位置的方块上，是不是每个方块都要存一份元数据？

当然不行——那样内存早就爆了。

解决办法的思路是：**99% 的时间里你只会用到 1% 的函数**，所以元数据的生命周期应该跟函数保持一致（函数没了，元数据随之释放），而不是跟方块绑定。

## 元数据访问链路

从 UI 到最终取到元数据，走的是这么一条链：

```text
1. package 代码片段组件（snippet widget）
2. 通过 behavior 传递
3. getPackageSnippets
4. level.getCapability(pos)  (IWenyanDevice)   ← 元数据挂在这里
5. IWenyanDevice.exec
6. exec.function/var  (Map<String, Value>)
7. value.type
```

这条链路设计得让**所有包都能用**，包括两类：
- 从 `getter (IWD)` 拿到的包；
- 文言函数本身的包。

## 落地计划

### Iter 1：先跑通

思路：`IWD → map<String, metadata>`，需要改这些地方：

- **访问方式**：给 `IWD` 加一个 metadata 接口，如果没有实现这个接口就做回退处理。
  ```java
  interface xxx { Meta getMeta(); }
  ```
- **新增部分**：用最简单的 AP（注解处理器）实现。包构建器：
  ```text
  build → record(package, meta)
  + buildMeta
  + build function
  ```
- **客户端侧**：`WenyanFunction` 拿到字符串 → 解析成 `ClientAST` → 得到 `getMeta`。

### Iter 2：收敛实现

`IWD` 的实现太多了，干脆把元数据挪到 **Raw package** 里，让它的生命周期和 `IWD` 保持一致，实现更清爽。

## 总结

WenyanDoc = 游戏内的「函数说明书 + 智能补全」系统。它让玩家不切屏就能查到函数用法、点一下就能补全整条语句，并通过「元数据生命周期跟函数走」的思路解决大规模方块下的内存问题。当前已规划了两期迭代：先做一个能跑的版本，再做收敛。

# 调试模式（Debug Mode）

> 名称暂定：**静滞墨**

## 概述

调试模式允许玩家按执行上下文逐步推进程序，观察函数调用和变量变化，并定位错误所在的语句。

目前尚未验证该功能的实际使用频率，因此第一阶段只实现最小可行版本（MVP），再根据测试结果决定是否扩展断点和变量检查能力。

## 功能

开启调试模式后，玩家可以打开一个调试 GUI，里面提供：

- **step（单步执行）**：走一步。
- **continue（继续）**：`<sub>continue</sub>`，直接跑完。
- **make breakpoint（设置断点）**：`<sub>make breakpoint</sub>`，在指定位置打点。
- **查看变量**：鼠标悬停时显示某个变量的当前值（`<sub>check one var's value when mouse hover</sub>`）。
- **exit（退出）**：直接回到编辑模式。

## 典型用户故事

想象一个场景：有个人写了段程序，但跑得太快，完全不知道是哪一步出了问题。他大致会这么用：

1. 先确认**没有程序在运行**。
2. 把符切到**调试模式**。
3. 打开调试 GUI。
4. **单步执行**，一步步看每个函数产出了什么结果。
5. 切回**编辑模式**，修改代码。
6. 重新运行，验证修好了没。

这个流程把「盲猜 bug」变成了「眼睁睁看着哪步出错」。

## 实现思路

核心改动在于**「step」的实现方式**：

- 改变现在 step 的做法，要求**程序提供上下文（context）给 step 使用**。
- **注入 step 函数**，维护一个 **PC（程序计数器）**，用来让程序停下来。
- 提供 `min(step, 剩余到 PC 的步数)` 这样一次步进量。
- 当玩家点击 step 时：`pc = 下一个 context.getEndPc`（也就是跳到当前代码块的结束位置）。

## 总结

调试模式通过调试界面提供单步、继续、断点和变量检查能力。第一阶段使用注入的步进控制与程序计数器实现 MVP，并根据测试结果决定后续扩展范围。
